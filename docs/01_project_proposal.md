# Section 1 — Project Proposal

## 1.1 Project Name

**CreditLens: ระบบ AI ช่วยพิจารณาความเสี่ยงสินเชื่อแบบอธิบายได้**
(Explainable AI-assisted Loan Default Risk Assessment)

## 1.2 Problem Statement

เจ้าหน้าที่สินเชื่อของธนาคารพิจารณาคำขอสินเชื่อรายย่อยด้วยดุลยพินิจและ checklist ที่ไม่สม่ำเสมอ แต่ละคำขอใช้เวลาหลายวัน
และผู้กู้กลุ่มที่ประวัติเครดิตน้อยมักถูกประเมินคลาดเคลื่อน ผลคือหนี้ที่กลายเป็น NPL ในปีแรกสูง (ในข้อมูล Home Credit มีผู้กู้ราว **8%**
ที่ประสบปัญหาการชำระ) ลูกค้าที่ดีต้องรอนานหรือถูกปฏิเสธโดยไม่มีเหตุผลที่อธิบายได้ ธนาคารต้องการ **ลดหนี้เสียจากสินเชื่อใหม่ ลดระยะเวลาพิจารณา
และให้เหตุผลประกอบการตัดสินใจที่ตรวจสอบได้และเป็นธรรม**

* **ใครได้รับผลกระทบ:** เจ้าหน้าที่สินเชื่อ ผู้ขอสินเชื่อ และธนาคาร (ผลขาดทุนและ reputational risk)
* **ปัญหาปัจจุบัน:** การประเมินช้า ไม่สม่ำเสมอ และอธิบายไม่ได้
* **ผลกระทบที่วัดได้:** อัตราผิดนัดชำระของสินเชื่อใหม่ ระยะเวลาต่อคำขอ และอัตราที่ผลการตัดสินใจไม่ตรงกันระหว่างเจ้าหน้าที่
* **ผลลัพธ์ที่ต้องการ:** การตัดสินใจเร็วขึ้น ความเสี่ยงต่ำลง อธิบายได้ และไม่เลือกปฏิบัติ

## 1.3 Justification for AI/ML

| เกณฑ์ | เหตุผลที่โจทย์นี้เหมาะกับ ML |
|---|---|
| **Big problem?** | สินเชื่อรายย่อยมีคำขอหลายแสนรายต่อปี ความเสียหายจากหนี้เสียมีมูลค่าสูง ระบบที่ดีขึ้นเพียงเล็กน้อยก็สร้างผลกระทบทางการเงินได้มาก |
| **Open-ended?** | ไม่มีสูตรตายตัวว่าใครจะผิดนัด ปัจจัย (รายได้ ภาระหนี้ อาชีพ อายุงาน คะแนนเครดิต) มีปฏิสัมพันธ์แบบไม่เป็นเชิงเส้น เขียนเป็น rule ได้ไม่ครบ |
| **Time-changing?** | พฤติกรรมผู้กู้เปลี่ยนตามภาวะเศรษฐกิจ ดอกเบี้ย และผลิตภัณฑ์ใหม่ โมเดลต้อง retrain ได้เมื่อมีข้อมูลผลการชำระใหม่ (feedback loop) |
| **Hard?** | ข้อมูลไม่สมดุล (default ~8%) มีค่าขาดหาย (คะแนนภายนอกหายถึง 56%) และมีความเสี่ยงด้านความเป็นธรรม มนุษย์เองก็ทำนายได้ไม่สม่ำเสมอ |
| **Partial solution acceptable?** | ใช่ ระบบออกแบบให้ **แนะนำ** ไม่ใช่ตัดสินใจแทน เจ้าหน้าที่ยังเป็นผู้ตัดสินใจขั้นสุดท้าย แม้โมเดลแม่นยำเพียง AUC ~0.75 ก็ช่วยจัดลำดับความสำคัญของงานและลดเวลาได้ |

**ทำไมไม่ใช้ rule-based อย่างเดียว:** rule เช่น “DSTI > 40% ปฏิเสธ” มองแค่ทีละปัจจัย ไม่รวมสัญญาณอ่อนหลายตัวเข้าด้วยกัน และปรับตามข้อมูลใหม่ไม่ได้
ML จึงเหมาะกว่า ส่วน rule ยังใช้เป็น business-rule validation ใน API เพื่อกันข้อมูลที่ขัดแย้งกันเอง
